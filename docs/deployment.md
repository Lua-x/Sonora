# Deploy Sonora with Docker

Sonora runs as a Docker Compose stack: PostgreSQL, a one-off migration container, the web app and a separate background worker. The published image targets **Linux/amd64**. The web UI is currently German.

## Configure and start

Follow the [quick start](../README.md#quick-start) to clone the repository and generate `.env`. No default password or usable secrets are shipped.

| Variable | Purpose |
| --- | --- |
| `POSTGRES_PASSWORD` | Random hexadecimal database password, generated by the setup script. Used when PostgreSQL initializes its volume. |
| `ENCRYPTION_KEY` | Exactly 64 hexadecimal characters for AES-256-GCM source-secret encryption. Keep it with your backups. |
| `SETUP_TOKEN` | Random token of at least 32 characters, required only for the first account setup. |
| `APP_URL` | Exact browser origin, such as `https://music.example.org`, with no path. Used for origin validation and secure cookies. |
| `PORT` | Host loopback port, default `3000`. Update `APP_URL` when changing it. |
| `SYNC_INTERVAL_MINUTES` | Default interval for new sources, normally 30 minutes. Each source can be configured separately. |
| `SONORA_IMAGE` | Optional GHCR release tag or digest; use with `--no-build`. |

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=80 web worker migrate
```

The migration container exits with code 0 on success. Web and worker wait for PostgreSQL health and successful migration. Applied migrations are checksum-checked: do not edit them in place.

Open `http://localhost:3000` on the Docker host, then use your `SETUP_TOKEN` from `.env` to choose your own account password. The default port binds to `127.0.0.1`; it is not exposed to the whole network. PostgreSQL has no published host port.

## Access from other devices

`localhost` always means the device opening the URL. If Docker runs on a server or NAS, access Sonora through a reverse proxy on that host using a hostname that resolves to it.

1. Set `APP_URL=https://music.example.org` in `.env` using your actual address.
2. Configure a host-based reverse proxy to forward to `127.0.0.1:3000`.
3. Recreate the app containers with `docker compose up -d web worker`.

Example Caddy configuration:

```caddyfile
music.example.org {
    reverse_proxy 127.0.0.1:3000
}
```

Point DNS to the server and provide the required HTTPS/certificate-validation ports. Browse using exactly the origin in `APP_URL`; requests that change state are rejected when their origin differs. HTTPS configuration enables the session cookie's `Secure` flag.

For a NAS-managed reverse proxy, use its equivalent hostname, HTTPS certificate and upstream settings. If the proxy itself runs in Docker, attach it deliberately to Sonora's Compose network and use `web:3000` as the upstream. Do not expose PostgreSQL.

## Published images and updates

To use the release image, set this in `.env`:

```dotenv
SONORA_IMAGE=ghcr.io/lua-x/sonora:0.1.0
```

Then:

```sh
docker compose pull web worker migrate
docker compose up -d --no-build
```

Image tags are `0.1.0` for the release, `main` for the latest passing main-branch build and `sha-<full-commit>` for a specific commit. Pin the published image digest when you require content-addressed deployment. If the package is private, use `docker login ghcr.io` with an authorized account and a token with `read:packages`; never put the token in `.env` or a command-line argument.

Back up before updating, read migration notes, then select the new release checkout and image together. A local source build uses `docker compose up -d --build`. All app roles use the same image with different startup commands.

Node and PostgreSQL base images are pinned by version and manifest digest. They use the public ECR mirror of Docker Official Images. Dependency versions are locked in `package-lock.json`.

## Back up and restore

A complete backup includes a PostgreSQL dump **and the matching private `.env`**, especially `ENCRYPTION_KEY`. The UI's JSON export contains listening history and metadata, not account credentials or the complete operational state.

Create a `backups` directory first. These commands avoid binary shell-redirection problems on Windows:

```sh
docker compose exec -T db pg_dump -U sonora -d sonora -Fc -f /tmp/sonora-backup.dump
docker compose cp db:/tmp/sonora-backup.dump ./backups/sonora-backup.dump
docker compose exec -T db rm /tmp/sonora-backup.dump
```

Date your backup, copy `.env` separately and keep both encrypted on another device. Do not copy a running PostgreSQL volume as a file-level backup.

**Restoring replaces the selected database contents.** Back up the current state first and practise on an isolated Compose project. Use the repository/image version and encryption key matching the backup:

```sh
docker compose stop web worker
docker compose up -d db
docker compose cp ./backups/sonora-backup.dump db:/tmp/sonora-backup.dump
docker compose exec -T db pg_restore -U sonora -d sonora --clean --if-exists --no-owner --exit-on-error /tmp/sonora-backup.dump
docker compose exec -T db rm /tmp/sonora-backup.dump
docker compose run --rm migrate
docker compose up -d web worker
```

Verify login, record counts and history dates afterwards. A PostgreSQL major-version upgrade requires a planned migration such as dump/restore or `pg_upgrade`, not just a new image tag.

## Health, persistence and shutdown

- PostgreSQL uses `pg_isready`; `/api/health` checks the app's database connection.
- The worker has its own database heartbeat healthcheck. A healthy web app alone does not prove that synchronization is working.
- SIGTERM gives the worker time to finish its current batch and close the database connection. Unfinished jobs remain stored and can resume after their processing lease expires.
- `docker compose down` preserves the database volume. **`docker compose down --volumes` deletes it.**
- `restart: unless-stopped` restarts crashed processes. A running container marked unhealthy is not automatically restarted by Compose; inspect the cause and restart after fixing it.

The first and latest stored event do not establish continuous coverage. Provider limits and known gaps are shown in the app. Configure your Last.fm or ListenBrainz account after setup; a successful container smoke test does not verify your provider account.

## Release pipeline

Pushes to `main` and version tags trigger typechecking, lint, tests, a production build, dependency audit, Docker build and a Compose integration test. The integration test checks setup, protected access, worker imports, repeated-import deduplication, the four calendar periods, export, retained data after container recreation and the isolated read-only demo.

Only successful checks allow the image to be published to GHCR. GitHub Releases are published separately with release notes and a version tag; publishing a container image alone does not create a GitHub Release. The workflow has read-only repository permissions by default; only the image publishing job receives package write access.
